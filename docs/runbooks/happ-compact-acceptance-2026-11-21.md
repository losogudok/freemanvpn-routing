# Happ compact JSON: персональное применение 2026-11-21

Компактная выдача применена только к существующему персональному правилу
`HAPP_PRIVATE_RUSSIAN_IP`. Общее правило `HAPP` продолжает выдавать
`XRAY_BASE64`. Общий переход пользователей не выполнен.

## Панель и автоматизация

Созданы и повторным GET проверены три шаблона:

| Назначение | Имя | UUID |
| --- | --- | --- |
| Обычные серверы | Happ Compact | `71bedbaa-5a4b-43a9-bd84-9de78f78a179` |
| Auto | Happ Auto Compact | `69aa8fcb-b075-49b5-a8bc-256ccf9d7bd7` |
| Российский IP | Happ Russian IP Compact | `8d992201-5fe0-4290-acaf-54fba009ee37` |

Два отдельных Host с тегом `HAPP_ONLY` используют существующие Auto и RU
inbound. Их UUID: `7b9d4c0a-b3a3-4403-b85b-d526c28bbc2d` и
`bcceb097-b95e-43fd-96d6-9aff4091e346`. Изначально они были выключены;
включены после сохранения фильтров Response Rules и проверки GET.
Существующие Host и общие шаблоны при применении не изменялись.

Персональное правило сохраняет свои условия и порядок перед `HAPP`,
выдаёт JSON, выбирает `Happ Compact`, сохраняет
`ignoreHostXrayJsonTemplate: false` и передаёт профиль
`routing: happ://routing/onadd/...`. Другие правила исключают `HAPP_ONLY`.
Персональная выдача исключает старые Auto и RU записи.

Сохранённая подписка содержит 10 конфигураций, размер тела — 25 548 байт.
Все конфигурации проходят Xray 26.11.9 с DAT из проверенного комплекта;
ссылки outbounds/balancers замкнуты, `remnawave` удалён панелью, Auto
содержит пять реальных proxy outbounds и `fallbackTag: block`.
GeoIP — `202611211053`, Geosite — `202611071812`.

Ответы этой же подписки для v2RayTun Android, v2RayTun Windows, INCY и
Xray Checker проверены до/после: тела побайтно одинаковы, управляемые
routing/geo-заголовки совпадают. Проверка общего Happ ограничена сохранением
Response Rule и фильтров: чужая подписка не использовалась для HTTP-проверки.

Три repository variables `REMNAWAVE_HAPP_TEMPLATE_UUID`,
`REMNAWAVE_HAPP_AUTO_TEMPLATE_UUID`, `REMNAWAVE_HAPP_RU_TEMPLATE_UUID`
установлены в GitHub и прочитаны обратно. Код локально закоммичен, без push;
новая автоматическая синхронизация начнёт действовать после публикации кода.
Рабочий workflow из GitHub в ходе этой приёмки не запускался.

## Pixel 8 Pro

Android 17; Happ 4.8.0, versionCode 2009; Wi-Fi.

Обновлена существующая подписка Freeman VPN. Happ показал
`All files have been successfully downloaded`. Для свежего импорта создана
отдельная временная подписка `Happ Compact Acceptance`: локальный HTTP
стенд через USB reverse передал точную копию реального JSON и routing header,
заменив только название группы. DAT URL остались настоящими закреплёнными
HTTPS URL FreemanVPN. Ранее этой тестовой группы не было. В ней виден
профиль `FreemanVPN JSON`; реальный Reality-профиль подключился, YouTube
`generate_204` вернул HTTP 204. Это свежая группа приложения, а не полный
сброс его данных. Хеши файлов внутри приватного хранилища телефона не читались.

| Проверка | Наблюдение |
| --- | --- |
| Обычный Reality, Netherlands 1 | CONNECTED; через SOCKS ядра телефона YouTube HTTP 204, GitHub HTTP 200, Yandex HTTP 302 |
| Обычный XHTTP, RU → Germany | CONNECTED; через SOCKS ядра телефона YouTube HTTP 204, Yandex HTTP 302 |

| YouTube напрямую в RU-профиле | Тайм-аут в текущей российской сети; доступность из-за границы не проверена |

Важная граница RU-проверки: Chrome с **выключенным** Happ показал тот же
публичный IP, что RU Host и IP-checker через RU. По выходному IP в этой Wi-Fi
сети нельзя различить direct и proxy. Отдельный локальный Xray с тем же RU
JSON/DAT и локальными заглушками выбрал `direct` для Cloudflare/GitHub;
общий checker ранее проверил 25 compact и 25 expanded сценариев, включая
специальные DNS-маршруты. Это доказательство правил ядра, а не всех
фактических маршрутов и DNS внутри телефона. Физический перехват DNS,
отсутствие утечек, FakeDNS на уровне пакетов и выход каждого RU-назначения
здесь не установлены. Общий серверный inbound по-прежнему имеет пересылку
в DE для части направлений; это применение не меняло серверный routing.

## Auto: отказ и fallback

Использована отдельная копия выданной панелью Auto-конфигурации на рабочей
машине с официальным Xray 26.11.9 и реальными endpoint. Адреса endpoint
заменены loopback TCP relay, чтобы создавать отказы только внутри стенда.
VLESS/Reality, правила, DNS, `leastPing`, selectors, `interval: 1m`,
`sampling: 3`, timeout и fallback сохранены. Локальные listener ports и
logging изменены только для проверки. Серверы и другие клиенты не отключались.

При отказе выбранного endpoint новые запросы к GitHub переключились на
другой `auto-proxy` и вернули HTTP 200. При отказе всего пула access log
показал `[socks -> block]`, запрос завершился отказом; намеренный direct-запрос
к Yandex вернул HTTP 302. Переключение происходило после обновления
наблюдений, а не мгновенно. Измерения одного прогона не задают гарантированное
время переключения. На телефоне проверено обычное подключение Auto;
отказ endpoint на самом телефоне не инжектировался.

Первый вариант стенда запрещал только новые relay-соединения; его результаты
не использованы как доказательство полного отказа endpoint. Итоговый прогон
также разрывал существующие соединения и прошёл все проверки. Один ранний
прогон был прерван вместе с исполнением команд и не считается завершённым.

## Пинг и оставшийся дефект

При подключённом VPN числовые результаты появились, включая обычные серверы,
Auto и RU. Например, Auto показал 197 ms, RU — 349 ms. После завершения
числовых результатов надпись `Ping checking` оставалась; смена соединения
сбрасывала её. Для Germany 2 в этом прогоне было `n/a`.

При отключённом VPN в свежей тестовой группе появились числа, включая
обычные серверы и Auto; например, Auto — 223 ms. Интерфейс вернулся в обычное
состояние, без зависшего `Ping checking`. Дополнительный финальный прогон
в рабочей подписке при выключенном VPN дал Auto 202 ms и RU 400 ms;
индикатор не завис. В снятом финальном буфере logcat
не найдено `FAILED BINDER TRANSACTION`. Это не полное исправление пинга:
сохранён дефект завершения проверки при активном VPN. Точная внутренняя
причина не установлена. Попытка разбора установленного APK через REA
остановилась на отсутствующем `REA_JADX_MCP_JAR`; приложение не изменялось.

## Итоговая граница приёмки

Персональное применение и реальные подключения трёх режимов выполнены.
Свежий импорт, обновление существующей подписки, компактная генерация,
API readback и откат в тестовом API, а также изолированные отказы Auto проверены.
Полная приёмка для общего перехода ещё не завершена: остаются connected-ping
UI, проверка RU из зарубежной сети и дополнительные измерения TUN DNS/FakeDNS.

Полные ответы с credentials, снимки для отката, временные конфигурации и
журналы находятся локально в `/tmp/happ-compact-implementation/` с ограниченным
доступом и не входят в Git. Для отката персональной выдачи восстановить
Response Rules из `apply-settings.before.json` и выключить два новых Host.

После проверки временная подписка удалена, тестовый HTTP-сервис и изолированный
Xray остановлены, USB reverse/forward стенда удалены, обе тестовые вкладки
Chrome закрыты. В Happ восстановлен Netherlands 1, VPN выключен.
